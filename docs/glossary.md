# 言葉の表

> 要約：このプロジェクトの文書、コードの注、報告で使う語の意味を1つに決めた表です。
> 「写し」「記録」「設定」のように、同じ語が別の意味で使われていたものは、呼び分けを決めて2章に置きました。
> 企画書、実装設計、開発計画に残っている別の言い方は直さず、5章に読み方を挙げています。

## 1 使い方

- 文書、コードの注、コミットの題、報告では、語をこの表の意味で使います。
- 新しい語を使うときは、先にこの表へ足します。
- 2章は、呼び分けを決めた語です。「写し」「補正」「モデル」「使用率」「枠」は単独で使わず、表の左の形で書きます。「設定」と「段」は、表の意味だけに使います。
- 「記録」も単独では使わず、何の記録かを必ず付けます（作業記録、タイムの記録、批評の記録、試作と実測の記録）。走行を残したものは「リプレイ」と呼びます。動詞の「記録する」はふつうの意味で使ってよいですが、走行を残すことは「録る」と書きます。
- 企画書、実装設計、開発計画には、決める前の言い方が残っています。直さずに、5章の読み方で読みます。
- 行番号は入れていません。出どころは、語で各文書を検索して引きます。

## 2 呼び分けを決めた語

同じ語が別の意味で使われていたので、次の形に決めました。

| 語 | このプロジェクトでの意味 | 使わない言い方・注意 |
| --- | --- | --- |
| ふるまいの写し | テストが基準として比べる、保存したファイル（`tests/snapshots/`）。指紋の写し、保存する項目の一覧の写し、正本の要約値の写しなどの総称。取り直しは単独のコミットで行い、変わった理由を添える | 「写し」と単独で書かない。ロジックの変更と同じコミットで書き換えない |
| ランタイムの写し | ブラウザ版のランタイムのファイルを手元に取得したもの（`.cache/` の下。gitの外）。ハッシュ値で照合する | |
| セッティングの対応 | セッティングの段階から、車両モデルと操作補正の値への対応（ステアリングだけは、操作補正の切る速さに掛ける倍率）。`cars.json` に持つ | 「セッティングの写し」「写し方」と書かない |
| 作業記録 | `docs/worklog.md`。頭に状態の表。決めた細目、検証の行、事後報告、次の手を書く | 「記録」と単独で書かない |
| タイムの記録 | ベストラップや最高順位など、保存するタイムのデータ。コース×レイアウト×車ごとに持つ | 「記録」と単独で書かない |
| リプレイ | 走行を記録したもの。全車の位置と姿勢を3 tickごと（毎秒20回）に残し、再生時に間を補間する。作ることは「リプレイを録る」「リプレイの記録（3 tickごと）」と書く | 走行を残す意味で「記録」と単独で書かない |
| 段 | 開発の単位。段0（立ち上げ）、段1（走りの核）、段2（リプレイとシアター）、段3（レース）、段4（仕上げと公開）。1段は区切り2〜13本が目安 | 開発の段のほかには使わない。ギアは「5速」「いちばん上のギア」、量子化は「256刻み」と書く |
| 段階 | セッティングと操作設定の選択肢の1つ。左から1、2、3…と番号を振る。セッティングは1〜5で3が標準（ステアリングだけ1〜3で2が標準）。操作設定は1〜5 | 「1段きつく」ではなく「1段階きつく」。開発の段を「段階」と書かない |
| 操作補正 | 入力フレームから、車両モデルへ渡す舵角とペダルの量を作る処理。遊びの除去、応答カーブ、車速に応じた最大舵角、カウンターの緩和、切る速さと踏む速さ。置き場は `cp_core/controls` | 「入力補正」「補正」と書かない。AI車は通らない |
| アシスト | ドライバー設定のONとOFFで切り替わる働き。ブレーキのロック防止、進入での巻き込み防止、駆動の絞り。エンジンブレーキの抑えは、入れるかを段1で決める。ペダルの量に上限を掛け、舵には手を出さない。置き場は操作補正と同じ `cp_core/controls` | 操作補正に含めない。「操作補正とアシスト」と並べて書く |
| セッティング | 車に対する6項目（ギア比、ウイング、サスペンション、ブレーキバランス、トラクション、ステアリング）を段階で選ぶもの。車×コース×レイアウトごとに保存する | 「設定」と書かない |
| 操作設定 | 入力機器の扱い（アナログ／デジタル）ごとに調整する8項目（調整項目）と、その画面。ペダルの割り当てもここで選ぶ | 項目は「操作設定のSTEER CURVE」のように書く。「ステアリングの項目」と書かない |
| ドライバー設定 | 変速（AT／MT）とアシスト（ON／OFF）の2つ。セッティングの画面で切り替える | |
| 設定 | 音量や表示など、セッティング、操作設定、ドライバー設定に入らないゲームの設定 | Claude Codeのほうは「Claude Codeの設定」と書く。動詞の「設定する」はふつうの意味で使ってよい |
| 検証 | 道具を回して確かめる作業の全体。絞った検証と全体の検証がある。報告は「回したもの（件数つき）」と「回せなかったもの」に分ける | |
| 検査 | 1つの道具やコードが行う、合否を返す調べ。層の分離の検査、はみ出しの検査、読み込み検査、リプレイファイルの検査 | リプレイファイルの確認を「検証」と書かない。「データの検査」ではなく「読み込み検査」 |
| テスト | pytestで回す自動テスト。ロジックのテストと守りのテスト。道具 `test` が回す | 運転役のテスト（drive）、通しのテスト（race-sim）、描画の巡回（tour）、音の回帰テストは、それぞれの名で呼び、単に「テスト」と書かない |
| 確かめ | 段の手順の1つ。批評の後、直した設計を独立の目で見る | 動詞の「確かめる」と、道具やテストが行う1つずつの「確かめ」（run の確かめ、など）は、ふつうの意味で使ってよい。段の手順を指すときは「設計の確かめ」と書く |
| 道具 | `tools/` に置く検証の道具。check、test、run、export、verify、web-smoke、screen-check、tour、drive、race-sim、selftest-break | 「ラッパー」と書かない。ReadやEditは「Claude Codeの道具」と書く。道具の名はハイフンで書き、ファイルの名は下線（`tools/selftest_break.py`、`tools/web_smoke.py`、`tools/screen_check.py`、`tools/race_sim.py`） |
| 実機 | 人の手元のPCやスマホ、実物のブラウザとコントローラー | この環境で動かして測ったことは「実測」「この環境で動かした」と書く |
| 視点 | 走行中に選ぶ見え方。後方追従とバンパーの2種類 | 「チェイス」「車載」と書かない |
| カメラ | リプレイで切り替わるもの（TVカメラ、後方追従、バンパー、ヘリ）と、3Dの描画で位置と向きを持つもの（`cp_core/camera`）。固定カメラは、TVカメラ用にコースデータへ置く点 | 走行中に選ぶものは「視点」 |
| 力の使用率／週の使用率 | 力の使用率は、車両モデルが出す輪ごとの量（前後は要求した力÷出せる力、横は滑り角÷最大グリップの滑り角）。週の使用率は、Claudeの週の枠に対する使用量の割合。週の枠は2つあり、週の使用率と言うときは、高いほうの値 | 「使用率」と単独で書かない |
| レースの枠／週の枠／コントローラーの枠 | レースの枠は、レースの6台それぞれの持ち場（「自車の枠もAIが運転する」）。週の枠は、Claudeの1週間の使用量の上限。セッションのイベントに `seven_day` と `seven_day_overage_included` の2つの欄で出る。コントローラーの枠は、ブラウザのGamepad APIが返す並び（`navigator.getGamepads()`）の1つずつ。つながっていない所は空になる | 「枠」と単独で書かない |
| 車両モデル／3Dのモデル／Claudeのモデル | 車両モデルは、車の動きを計算する自前のモデル（車輪の回転を状態に持たない4輪モデル）。3Dのモデルは、形の表から生成する車や景観物の形。Claudeのモデルは、セッションを動かしているClaudeの種類 | 「モデル」と単独で書かない |

## 3 言葉の表

### 進め方と文書

| 語 | このプロジェクトでの意味 | 使わない言い方・注意 |
| --- | --- | --- |
| 区切り | 段の中の作業の単位。実装、絞った検証、レビュー、直し、作業記録、コミットを1組とする。1区切り＝1コミット＝1回のレビュー。終わりは「コミットしてpushするまで」 | 「切れ目」（段の間）、「節目」（計画を見直す時点）とは別 |
| 通過条件 | 段を終えて次へ進むために満たす条件。実機での確認を含む | コースの「通過点」とは別 |
| 縦切り | 段0の最後に作る、車1台が仮の周回路を走る最小版。ブラウザ版の速度と画面の方向を確かめるために作る | 「最小版」と書かない |
| 批評 | 段の手順の1つ。設計の下書きを、観点ごとのレビュー役と反証役が読む。採否は主のエージェントが決める | 区切りごとの差分の「レビュー」とは別の手順 |
| 反証役 | 批評の中で、レビュー役の指摘を疑って確かめ直す役 | |
| 段の仕上げ | 段の最後の手順。全体の検証を回し、文書と規則ファイルを整える | 段4の名「仕上げと公開」とは別 |
| 詰み | 走れない、進めない、戻れない状態。見つけた時点で直し、事後報告にする | |
| 正本 | 企画書（`docs/canon/planning.md`）。人が採った改訂案を当てる単独のコミットのほかでは書き換えない | 「正本の写し」と書かない |
| 改訂案 | 正本と実装のずれなどを書いてためるもの（`docs/proposals/`）。反映は人が決める | |
| 作業の控え | `docs/handoff.md`。25行まで。区切りのコミット、途中のコミット、止める前に上書きし、再開のとき最初に読む。「控え」と略してよい | |
| 常設の方針 | 着手前の伺いへの回答と、後からの指示を、方法と理由の形で残したもの（`docs/standing-policy.md`） | |
| 伺い | 人に判断を求めること。方向（遊び方、表示の方式、正本の変更）だけを伺い、細目は推奨で決めて作業記録の事後報告に書く | |
| 仮の値 | 後で合わせる前提で置く値。定義データの `_notes` に `仮の値：<根拠>。<合わせる時>` と書く。出荷するコードに置いてよいのは、定義データをまだ読めない所だけで、`# 仮の値：<根拠>。<合わせる時>` と書く。合わせるのは段4 | 土台の値（設計の前提）は仮の値にしない |
| 割り切り | 限りを承知で簡単にした所。コードの注に `# 割り切り：<限り>。<見直す時>` と書く | 決まりを外す書き方には使わない |
| 初期版 | 車4台、コース1本（アカネ・ショートの順走）の版。HTMLファイルを渡すところまで | 「初期版の公開」はこの受け渡しのこと。Webに置くことは「Webへの公開」と書く |

### Claude Codeの構成

| 語 | このプロジェクトでの意味 | 使わない言い方・注意 |
| --- | --- | --- |
| 規則ファイル | 分野にだけ効く決まりを書くファイル（`.claude/rules/<分野>.md`）。その分野の最初のファイルを作る区切りで足す | ゲームの決まりは「ゲームの規則」と書く |
| 分野 | 決まりと検証をまとめる、コードの受け持ちの単位。規則ファイルの名（vehicle、track、controls など）と、検証の組の表の行に使う。触れた分野は、変更したファイルから `tools/verify` が引く | |
| サブエージェントの型 | サブエージェントの役目と約束を決めたもの。実装役、レビュー役、読み手の3つ | 「型」と単独で書かない（データの型と紛れる） |
| 実装役 | 設計の1区切りを実装し、絞った検証を回して報告する型。コミットもpushもしない | |
| レビュー役 | 与えられた観点で設計か差分を読み、起きる場合を添えて指摘する型。読むだけで、道具を回さない | |
| 読み手 | コードや文書を読んで、領域の地図や要約を返す型。何も書き換えない | ファイルを読むプログラムは「読む側」と書く |

### 構成と時間と描画

| 語 | このプロジェクトでの意味 | 使わない言い方・注意 |
| --- | --- | --- |
| tick | 時間の単位。1 tick = 1/60秒の固定刻み。入力、操作補正、物理、AI、レースの時計はtickで進む。更新1回が1 tick | `cp_core` はフレーム番号や実時間を読まない |
| 実描画 | 間引きを通って実際に行う描画1回。毎秒30回。前回の実描画から2 tick以上、または1 tick以上かつ30 ms以上たったときだけ行う | 更新（毎秒60回）とは回数が違う |
| 裏画面 | 3DとHUDを描く320×240の画面。毎回、これを画面へ写す | |
| 層 | アプリの3つの重なり。`cp_core` は規則と状態（純Python）、`cp_ui` は2Dの画面の組み立てと検査（純Python）、`cp_app` はPyxelとブラウザに触れる部分。`cp_app` → `cp_ui` → `cp_core` の向きにだけ呼ぶ | `cp_core` と `cp_ui` は、Pyxelもブラウザも実時間も参照しない |
| ロジック／純Pythonの層 | ロジックは `cp_core`（規則と状態）。純Pythonの層は、`cp_core` と `cp_ui` をまとめて言う語。どちらもPyxelなしでテストできる | `cp_ui` を「ロジック」に入れない。Pyxelに触れる側は「`cp_app`」と書き、「表示側」と書かない |
| 出荷物／配布物 | 配布物は、人に渡すHTMLファイル1本。出荷物は、その中に入るもの（`clipping_point/` の下だけ） | テスト、道具、文書は出荷物に入れない |
| ランタイム | ブラウザ版でPyxelを動かす実行環境（PyodideとPyxelのWebAssembly版）。起動時にネットから読み込まれる | 「実行環境」と書かない |
| デスクトップ版／ブラウザ版 | Pyxelの2つの動かし方。開発とテストはデスクトップ版、配布物はブラウザ版。浮動小数の結果は一致しない前提で作る | 「Web版」と書かない。「版」は何の版かを付ける（Pyxelの版、データの版、初期版） |
| 描画命令 | `cp_ui` が組み立てる2Dの描画の指示（文字、矩形、縁だけの矩形、線。画像は、使う画面を作る区切りで足す）。`cp_app` がPyxelで実行する。2Dの描画は必ずこれを通す | |
| 囲み | 描画命令をまとめる範囲（パネル、一覧の行、HUDのまとまり）。`Canvas.box` で宣言し、何も描かない。中の描画命令は、囲みの内に収まっていなければ、はみ出しになる | 「枠」と書かない |
| 縁だけの矩形 | 中を塗らない矩形の描画命令（Pyxelの `rectb`） | 「枠」と書かない |
| インクの箱 | 文字の描画命令が、実際に画素を置く範囲の矩形。幅は 4×（いちばん長い行の字数）−1、高さは 6×行数−1（最後の行に g j p q y があれば 6×行数） | 文字のセル（1字が4×6）とは違う |
| 表示用の値 | 画面の組み立てに渡す値。画面ごとに、書き換えられない型で持つ。描く側は、受け取って描くだけ | |
| 音の要求 | `cp_core` が毎tick 1つ出す、音についての値。`cp_app/audio` が音源へ反映する | |
| 世界 | `cp_core/sim` が持ち、1 tickずつ進める状態の全体 | 「世界座標」は車体座標に対する語で別 |
| 画面の状態 | `cp_core/flow` が持つ、いまの画面とその中の値（カーソル、選択値、再生位置）。描く側はこれを描くだけ | 作業の進み具合は「状態の表」（作業記録の頭）。「状態」は何の状態かを付ける |
| 決定性 | 同じ入力から同じ結果が出ること。`cp_core` はtickだけで進み、乱数は用途別に分ける | |
| 定義データ | 調整する値をコードに埋めずに出したJSON（`clipping_point/data/`）。読み込むときに必ず読み込み検査を通す | 試験用データ（`testpacks/`）は、重ねて試すためのデータで、出荷物に入れない |
| 保存の口 | 出荷するコードが、保存に使う1つの口（`cp_core/storage` の `SaveStore`）。値に封筒を付けて、保存先へ渡す。使う側は、保存先の違いを知らない | ファイルや localStorage を、直に触らない |
| 保存先 | 値を実際に置く所。メモリ、ファイル、localStorage の3つ。どれも、読む、書く、消す、鍵の一覧の4つを持つ。ブラウザ版は、起動時の試し書きで、localStorage が使えなければ、メモリへ切り替える | |
| 封筒 | 保存する値に付ける、印、形式バージョン、長さ、チェックサム。読めない封筒は、壊れた値として扱う（別名へ退避して、既定値で書き直す） | |
| 乱数の流れ／ハッシュの抽選 | 乱数の流れは、用途ごとに分けた乱数の列（`cp_core/rng`）。ハッシュの抽選は、種と鍵から決まる、状態を持たない抽選。新しく足す仕組みは、ハッシュの抽選を使い、いまある流れを引かない | 標準の乱数と、組み込みの `hash()` は使わない |
| 口 | ある部分が、外から呼ばれたり値を受け取ったりするために決めた形。保存の口、車両モデルの口 | 画面への「入口」、コーナーの「出口」はふつうの意味 |
| 鍵 | 値を引くための名。定義データ（JSON）の鍵と、保存の鍵（保存先での名）がある | どちらの鍵かを付ける |

### 入力と操作補正

| 語 | このプロジェクトでの意味 | 使わない言い方・注意 |
| --- | --- | --- |
| 入力フレーム | 毎tick 1度だけ入力を読んで作る、正規化した入力。舵、アクセル、ブレーキのアナログ値とデジタル値、ボタン類の「押している」「押した瞬間」を持つ | |
| 入力アダプタ | 機器ごとの差を吸収して入力フレームを作る部分（`cp_app` の `input_pyxel`）。値の範囲をそろえるだけにする。ブラウザ版のトリガーは、直読み（`input_web`）の結果を受け取って入れる | 遊びの除去と応答カーブは操作補正に置く。直読みは、入力アダプタに数えない |
| アナログ操作／デジタル操作 | スティックやアナログのトリガーでの操作と、キー、十字キー、ボタン、画面上パッドでの操作。どちらの値を使うかは操作補正が毎tick決める | 「アナログ入力」「デジタル入力」と書かない。入力フレームの中の値は「アナログ値」「デジタル値」 |
| 遊び | スティックの中央で、入力を0と見なす範囲。操作設定のDEAD ZONE | |
| 応答カーブ | 入力の量に対する効きのカーブ。式は y = x + k(x³ − x)。ステアリング、アクセル、ブレーキに別々に持つ | 「踏み込みカーブ」「補正カーブ」と書かない |
| 車速に応じた最大舵角 | 速度が上がるほど絞る、舵角の上限。略すときは「舵の上限」 | 「上限」と単独で書かない。車が持つ限り（31.5度）は「車の最大舵角」。「切れ角」と書かない |
| カウンターの緩和 | 後輪が滑っていて、立て直す向きに切ったときだけ、舵の上限を広げ、切る速さを上げること。操作設定のCOUNTER | 「カウンターステアの優先」と書かない |
| 切る速さ | 実際の舵角を目標へ近づける速さ。舵の上限に対する割合で決める。ペダルのほうは「踏む速さ」 | 「舵の速さ」「車側の舵の速さ」と書かない |
| 台本 | 入力フレームを時刻順に書いたもの。テストと画面なしの実行で差し込む。指紋テストの台本は、段1から運転役が走らせる形にする | 作業用のものは「スクリプト」と書く |
| 区間 | tickで区切った、ひと続きの間。台本の区間（同じ入力が続く）、偽のコントローラーの予定の区間（同じ状態が続く。「予定の区間」と書く）、処理時間を測る区間。長さはtick数で持つ | 「段」と書かない（「段」は開発の段だけ） |
| 直読み | ブラウザ版で、Pyxelをはさまずに、ブラウザのGamepad APIからトリガーの値を読むこと（`cp_app` の `input_web`）。標準の並びのコントローラーでだけ使う。Pyxel経由では、トリガーが0か最大かの2値でしか届かないため | デスクトップ版では使わない |
| 標準の並び | ブラウザが、コントローラーのボタンと軸を決まった順に並べて渡している状態（Gamepad APIの `mapping` が `standard`）。左トリガーはボタン6、右トリガーはボタン7 | |
| 入力の要約値 | 世界が受け取った入力フレームを、毎tick量子化して畳み込んだ整数（世界の要約の `input_digest`）。入力が世界へ、順のまま届いたことを確かめるのに使う | 指紋（全車の状態の要約）とは別 |
| 入力の跡 | 検証のときにアプリが残す、入力フレームの変わり目の列（tickと、量子化した値）。煙テストが、台本や偽のコントローラーの予定と照らす | 「入力の記録」と書かない（リプレイの記録と混ざる） |
